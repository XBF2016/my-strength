# 独特优势记录协议

## 核心定义

以后所有记录和讨论，都只围绕这 3 个定义标准：

1. 长期可持续：这类事情我能长期稳定做下去。
2. 学习速度更快：在这类事情上，我比多数人更快抓住关键、上手、形成方法。
3. 做得更好且有外部验证：结果更好，而且这种“更好”能被现实中的反馈、信任、机会、责任、合作或其他外部结果稳定证明。

补充说明：

- 兴趣、热情、历史积累、环境、资源，都不是“独特优势”的定义本身。
- 它们可以作为证据、背景或解释，但不能替代上面这 3 个定义标准。

## 新的协作分工

以后默认采用“先探索，后归档”的两阶段协作：

- `$unique-advantage-explorer`：用于把一个新案例聊清楚，区分事实、解释、感受和猜测，判断它是否已经准备好进入正式记录。
- `$unique-advantage-journal`：用于把已经澄清并且用户同意归档的内容写入档案，并维护索引和总览。
- `$unique-advantage-cleaner`：用于列出、删除、清空、迁移或重建档案索引。

默认路径是：

1. 你先自然讲一个案例、片段、困惑或直觉。
2. Codex 先使用 `$unique-advantage-explorer` 跟你来回探索，帮助你把这个案例讲透。
3. 当事实、行动、结果和外部反馈已经足够清楚时，Codex 再建议你是否进入正式归档。
4. 只有在你明确同意时，Codex 才使用 `$unique-advantage-journal` 写入文件。

## 探索优先原则

不是所有口述内容都直接进入正式案例库。探索阶段先做这几件事：

1. 先区分事实、解释、感受或想象，不急着评分。
2. 一次只追问 1-3 个最高杠杆的问题，不做问卷式审讯。
3. 优先澄清具体行为、关键选择、结果、外部反馈，以及它是不是重复出现的模式。
4. 如果证据还不够，就先说明还缺什么，而不是硬下结论。

## 归档门槛

探索之后，把材料分成三类：

1. 事实案例：真实发生过，有具体行为、结果或外部反馈，可以进入正式案例区。
2. 混合案例：既有真实事件，也夹杂解释、判断或设想，需要再澄清一两个关键点后决定是否入库。
3. 假设线索：主要是偏好、设想、预测、自我描述，暂时缺少完整真实事件支撑，只进入“假设线索”区，不当作正式证据。

只有满足下面条件之一，才适合进入归档：

- 正式案例：存在真实事件，并且对三项定义中的至少一项已经有可用事实证据。
- 假设线索：内容有启发，但证据还不足以成为正式案例。

如果材料还停留在“说不清”或“感受很多但事实很少”的状态，优先继续探索，而不是立刻写入。

## 固定流程

以后每次协作，默认按这 6 步走：

1. 我先讲一个新案例、片段或判断。
2. Codex 优先使用 `$unique-advantage-explorer` 复述理解，并区分事实、解释、感受或猜测。
3. 如果信息不够，Codex 只问最关键的 1-3 个问题，把案例讲清楚。
4. 当案例已经足够清楚时，Codex 明确提示我：现在是否要正式归档。
5. 只有我明确说“记录”“归档”“写进去”之类的话，Codex 才使用 `$unique-advantage-journal` 写入 `strength-system/`。
6. 每次写入后，都要同步更新 `strength-system/case-index.json` 和生成总览。

## 索引规则

这个系统现在有五个数据层：

1. `strength-system/cases/`
这里存放所有正式案例文件，每个案例一个文件，这是正式案例的真实源。

2. `strength-system/hypotheses/`
这里存放所有假设线索文件，每条线索一个文件，这是低证据线索的真实源。

3. `strength-system/reviews.md`
这里存放跨案例复盘记录，这是复盘结论的真实源。

4. `strength-system/case-index.json`
这是自动生成的辅助索引，用来加速列表、清理、统计和复盘。它应该尽量轻量，只保留定位和摘要所需的信息。

5. `strength-system/case-library.md`
这是自动生成的人类可读总览，用来快速浏览，不是真实源。

规则是：

- 不允许只改索引或总览，不改源文件。
- `cases/`、`hypotheses/`、`reviews.md` 变化后，必须立即重建索引和总览。
- 索引应保持摘要化，避免重复存储展示型字段。
- 如果索引或总览缺失或过期，必须从源文件重建。

## 三项评分规则

每条正式案例都要对这 3 项分别打分，范围是 `0-2`：

- `0`：证据不足，暂时无法判断。
- `1`：有一定信号，但证据不够稳定或不够强。
- `2`：信号明确，证据较强。

对应项目：

- 长期可持续性
- 学习速度优势
- 外部验证的更优结果

## 正式记录格式

每条正式案例都按下面这个结构整理：

```markdown
## 正式案例 00X - 案例标题

- 日期: YYYY-MM-DD
- 来源: 用户口述案例
- 长期可持续性评分: 0-2
- 学习速度评分: 0-2
- 外部验证评分: 0-2
- 初步判断: strong signal | possible signal | insufficient evidence

### 事实

### 长期可持续性信号

### 学习速度信号

### 结果与外部验证

### 备注
```

## 假设线索格式

当内容主要是设想、偏好、预测，而不是已经发生并可验证的事实时，按下面格式记录：

```markdown
## 假设线索 00X - 标题

- 日期: YYYY-MM-DD
- 来源: 用户口述线索
- 状态: 假设线索

### 这条线索说明什么

### 为什么还不能算正式证据

### 需要什么证据来升级
```

## 推荐起手方式

如果我想先把案例聊清楚，可以这样说：

`请使用 $unique-advantage-explorer，先和我把一个新案例聊清楚，区分事实、解释和感受，暂时不要急着归档。`

如果我已经聊清楚了，只想正式写入档案，可以这样说：

`请使用 $unique-advantage-journal，先读取 strength-system/protocol.md 和 strength-system/case-index.json，然后把这个已经澄清的案例正式记录进我的档案。`
